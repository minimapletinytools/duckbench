Project explorer and agent for Duckbench

Borrow Kigumi’s panel layout, file navigation and edit review. Organize Duckbench around the Python file being edited, the script that builds the model, and the build that produced the visible geometry.

The first release in one project

A bracket has two files. model.py creates the solid and imports width from dimensions.py. While looking at the helper, the user asks the agent to widen the bracket from 24 to 36 mm.

Projects, browser storage and export

Projects stays visible at the top of the explorer. In the browser, it opens the named project list with Create, Open, Delete and Export ZIP. Import Folder brings the supported files into a new project. In the desktop app, Open Folder works directly with files on disk.

Browser files already autosave in IndexedDB. Each project has its own ID and relative file paths. Reopening Duckbench restores the last project and active file. Keep the save indicator and protection against overwriting edits from another tab. Show “Saved in this browser” beside the project name so users know why a ZIP backup matters before clearing site data. Projects remain usable while signed out.

  • Project menu → Export project ZIP. Keep the existing editable source archive. Add Import project ZIP in phase 1 so a downloaded project can be restored directly. A small versioned manifest can carry the project name, active file and run target. Accept older source-only ZIPs too. Restore into a new project ID so an existing project with the same name survives.
  • File menu → Download file. Keep the browser shortcut for someone who only wants one source file.
  • Preview → Export STEP or STL. Keep geometry export beside the built model. Show which successful build will be exported if the user has edited the source or a subsequent build failed. The future standalone viewer is a fourth export choice for sharing an interactive preview.

Phase 1 acceptance. Create two named projects containing a file with the same name. Edit one, reload and verify both retain their own contents. Export a project with a nested helper, then import its ZIP into a fresh browser profile. The restored project should rebuild with the same relative imports and run target.

What to borrow from Kigumi

  • Explorer. Adopt its compact project header, expandable folder rows, keyboard navigation and actions on the selected row. Give Duckbench one primary tree of real project files. Kigumi’s Frames and Patterns sections depend on its timber-frame model. Duckbench’s assembly hierarchy already has a home in the 3D viewer.
  • Agent. Adopt its conversation-first layout, model picker, history, file mentions and inline diffs. Put account and MCP setup behind a disclosure, with a visible connected indicator and access to Disconnect. Keep Stop beside the composer during a turn. On narrow screens, the explorer and agent can each occupy the available width and return focus to the editor when closed.
  • CAD behavior. A single-file project runs the active Python file as it does today. For a multi-file project, offer Set as run target on a Python file. Show its name on Run and remember it per project. Opening a helper leaves the chosen target in place. Distinguish the last successful preview from a stale or failed build.

Delivery order

1. Make file navigation and Run agree

Put project switching, folder import/open and ZIP export in the explorer’s project menu. Keep Run, Stop and CAD exports near the preview. Give the tree named file creation, active and unsaved indicators, a context menu and Arrow-key navigation. Extend the existing ⌘P / Ctrl+P search with selectable matches. Persist expanded folders and the optional run target per project. Desktop gets Reveal in Finder or Explorer, and browser projects keep Download file.

Acceptance. Open dimensions.py using the keyboard, run the pinned model.py, reopen the project and recover the target. If the target was removed, prompt for a new target before building. An existing single-file project still works without setup.

2. Review a real CAD edit end to end

Let the user attach a file with @ or Ask agent about this file. Display the files read during the turn and a unified diff with the project-relative path. Extend the current one-edit proposal to any text file in the selected project, one file at a time. Give chat and external MCP clients the same proposal and build-result tools. A build result should include the target, success or failure, project traceback locations, and which build is still on screen.

Acceptance. With model.py open, propose the width change in dimensions.py. Apply edits the source and marks the preview stale. Apply & Run builds model.py using that change. If the source changes after review starts, request a fresh diff. If the build fails, a traceback link opens the project file at the failing line and the previous geometry stays visible.

Desktop detail. Today Electron runs the active source buffer but Python imports sibling files from disk. For the first release, offer Save changed files & Run when imported helpers may be unsaved. Browser builds can use the current project buffers. On desktop, clicking Apply alone leaves the edit unsaved. Native execution stays an explicit user action.

3. Resume work across sessions

Add locally saved conversations scoped to the project and signed-in account, a history picker, restored drafts, and model selection from the existing Worker catalog. Store browser history by project ID and desktop history in application data keyed to the folder. Restore past edit decisions as history. A fresh edit always checks the current file.

Acceptance. Reopen the bracket project and resume its conversation. Switch to another project or account and its history is separate. Switching projects also disconnects the previous MCP session.

4. Share a standalone viewer

Start with Export interactive viewer (.html) from a successful preview. The recipient opens one file in a browser, orbits, pans and zooms the model, and toggles parts in the assembly tree. Bundle the display geometry, labels, colors and viewer assets in the file so it opens offline without an account, Python, or access to the author’s project.

Duckbench already passes a tessellated scene from the Python runner to the JavaScript viewer. In phase 1, retain that scene with its successful build identity. In phase 4, build a read-only viewer entry point around the same renderer and a versioned scene format. Keep source files, chat and credentials out of the export. The same entry point could later power a dedicated desktop viewer. Opening arbitrary STEP or STL files directly would additionally require importers for those formats.

Acceptance. Export a two-part assembly, close Duckbench, and open the HTML in a fresh browser profile with the network disconnected. Both named parts should appear, orbit correctly and toggle independently.

Implementation and scope

Give the explorer, chat and MCP a shared interface for project-relative paths, editor buffers and file revisions. Build that interface on Duckbench’s existing Electron and IndexedDB implementations. Extend the existing build path to accept a target independent of editor focus and record the last attempted and successful builds. The browser relay, local MCP transport, Worker and shared Supabase login can stay as deployed.

Ship phases 1 and 2 as the first milestone. Defer batch refactors, project-wide checkpoints, geometry-selection attachments and a catalog of runnable models until the two-file workflow works well on both hosts. Renaming files and folders can follow once dirty buffers, imports and pinned targets have defined behavior.
